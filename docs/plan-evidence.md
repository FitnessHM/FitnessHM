# Plan generator — rule sources

Every rule the plan generator (`src/lib/plan/`) enforces, with where it
comes from. Labeled plainly as **research** (a real citation, with the
caveat the research itself doesn't always claim) or **convention**
(standard coaching practice / a reasonable engineering default, not a
controlled study) — never a fabricated citation. See
`docs/superpowers/specs/2026-11-21-phase2-plans-design.md` for the full
design this implements.

| Rule | Where it's implemented | Source |
|---|---|---|
| ~80% of weekly volume easy, ~20% moderate/hard | `volume.ts` (`maxHardSessionsPerWeek`, `includeModerateSession`), `generate.ts`'s slot selection | **Research-informed.** The polarized-training distribution observed in elite endurance athletes (Seiler, "Intervals, Thresholds, and Long Slow Distance," and the broader polarized-training literature it's part of). Applied here as a target for recreational athletes of every level, which that literature doesn't itself validate — convention-by-extension, not a direct finding. |
| Max 2 hard sessions/week (1 for beginners) | `volume.ts::maxHardSessionsPerWeek` | **Convention.** Widely used in popular structured-training methodologies (e.g. Daniels-, Pfitzinger-style plans) across disciplines. No single controlled study cited. |
| Never two hard/moderate ("non-easy") days back-to-back | `generate.ts`'s adjacency check (`lastNonEasyDate`, `hasNonEasyFixedOn`) | **Convention.** Standard hard/easy alternation practice for recovery between quality sessions. Not a specific citation. |
| No hard sessions on a lifting/sport day | `generate.ts`'s `canBeHardToday` check against `Athlete.otherTrainingWeekdays` | **Design choice.** Avoids compounding fatigue across modalities on the same day. Not drawn from a study. |
| A deload week every 3–4 weeks | `phases.ts` (`isDeloadWeekIndex`, every 4th week, never the first) | **Convention.** Common 3:1/4:1 build:recovery week cycling used across structured-training methodologies (running, cycling, rowing alike). |
| Deload week: ≤1 hard session (0 for beginners), volume ≈ 65% of a build week | `volume.ts::maxHardSessionsPerWeek`, `phases.ts`'s `volumeFactor: 0.65` for deload weeks | **Convention.** Ballpark reduction consistent with typical deload-week guidance; not a precise literature figure. |
| Longest session this week ≤ 110% of the max of the last ≤3 non-deload/taper weeks | `volume.ts::longestSessionTarget` (`GROWTH_CAP = 1.1`) | **Convention, explicitly caveated.** A conservative reading of the popular "10% rule." That rule itself has **weak controlled-research support** and is widely criticized as a popularized heuristic, not a validated prescription — used here as a ceiling, never a target, precisely because of that weak support. |
| Taper length scaled to event length (by estimated finishing time) | `phases.ts::taperWeeksFor` + `estimateFinishMinutes` | **Convention.** Commonly seen taper lengths (a few days for 5K/short-event-length efforts, 1–2.5 weeks for marathon/century-length efforts), not a single source. The "estimated finishing time" itself uses one flat rough-speed-per-discipline assumption (`ROUGH_SPEED_KMH`) rather than a true per-level pace model — a deliberate simplification: it only needs to land in the right bucket, not be accurate. |
| Base 40% / Build 35% / Specific 25% phase split (of the weeks remaining after taper) | `phases.ts::buildRacePhases` | **Convention.** A simplified classic base/build/peak periodization structure (in the spirit of Friel's *Training Bible*-style plans), not a precise prescribed ratio from research. |
| Fewer than 3 weeks remaining after taper → skip straight to "specific" | `phases.ts::buildRacePhases`'s `remaining < 3` fallback | **Honest fallback**, not a researched threshold — there's no real room for a base/build progression in that little time, so the generator says so rather than pretending otherwise. |
| General-fitness/weekly-hours blocks: repeating 3 build weeks + 1 deload week | `phases.ts::buildBudgetPhases` | **Convention.** Same build:recovery cycling as the race-goal deload rule, applied continuously rather than inside a race-specific phase structure. |
| Week 1 of a general-fitness block ramps in at ~80% of target volume (100% for a baselined non-beginner) | `phases.ts::buildBudgetPhases`'s `volumeFactor: i === 0 ? 0.8 : 1` | **Design choice.** Avoids a hard opening week; not a researched number. |
| Starting ("seed") longest-session duration by level, when there's no history yet | `volume.ts::PEAK_LONG_SESSION_SECONDS` | **Convention.** Ballpark defaults (beginner 35 min → competitive 120 min), not measured — a seed the growth cap then governs, not a target in itself. |
| Each week's "long" session lands on the latest available training weekday | `generate.ts`'s `longDate` selection (last open date in the week's training-weekday list) | **Placeholder convention.** This app doesn't collect which day an athlete actually has more free time; "last available day of the week" is a reasonable default, not a personalized choice. |
| Mix blocks: the primary (goal) discipline gets roughly double the weekly share of any secondary discipline, and every discipline appears regularly even with fewer weekly slots than disciplines | `mix.ts` (`DisciplineCycle`, `buildDisciplineShares`) | **Design choice.** A weighted-fair-interleaving scheduler (classic weighted round-robin), substituting for the spec's exact ceil/floor "remainder to primary" language with the same intent, simpler to implement correctly for any slot count. |
| A discipline with no hard-tier type (swimming, walking) never gets a "hard" slot — it downgrades to that discipline's moderate type | `library/common.ts::buildSessionFromProfile`'s slot downgrade | **Reads the given per-discipline library literally.** Swimming's toughest listed type is threshold/CSS (moderate); walking's is hills (moderate). Neither library lists a harder type, so the generator doesn't invent one. |
| With no baseline, a discipline's checkpoint test takes the place of its first safely-schedulable hard/moderate session (not forced onto day 1 regardless of budget/adjacency) | `generate.ts`'s `isCheckpointOpportunity` / `checkpointContent` | **Design choice**, refined during testing: an earlier version forced the checkpoint test onto the literal first calendar day regardless of the week's hard-session cap or adjacency rule, which could itself violate both. Gating it through the same budget/adjacency check a normal hard/moderate session goes through fixes that. |
| Cycling never gets a numeric pace/power target, only a descriptive zone label + RPE | `library/cycling.ts`, `library/common.ts` (`unitDistanceMeters: null` path) | **Honest scope limit**, not a convention with a source. No power meter or cycling-specific field test exists in this app, so there's no baseline to derive a number from — see the spec's Non-goals. |
| Running/walking pace, swim pace-per-100m, and row split-per-500m targets, once a baseline exists | `paceMath.ts::trainingZonesFromBaseline`'s `ZONE_PACE_PERCENT` table (percent of threshold pace per zone), reused unchanged across disciplines — only the unit-distance denominator (1000/100/500) changes | **Convention**, carried over from Phase 1: standard percentage-of-threshold-pace training-zone bands. Phase 1's own spec already flagged these as "a simplification... later phases may want to make them user-editable." Still true here. |
